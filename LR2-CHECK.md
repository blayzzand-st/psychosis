## Текущий статус: дефект сохранения после refresh исправлен

Разрешение редактирования теперь связано со стабильным семейством сессии:
`user_refresh_tokens.family_id` / JWT `sid`. При refresh `jti` меняется, `sid`
сохраняется; при новом входе возникает другое семейство. Поэтому refresh не
ломает ранее выданное разрешение, а использовать его в другой сессии нельзя.
Проверки роли, аккаунта, auth_version, срока и версии ЭМК сохранены.

Миграция заполняет family_id существующих refresh значением их id, не удаляя
сессии. Старые JWT без sid поддерживаются через соответствие sid=jti.
Для разрешений, которые уже стали непригодны до исправления из-за прежней ротации,
нужно получить новую разблокировку.

После исправления прошёл полный набор **251 backend-тест**, затем отдельно две
целевые проверки: миграции существующей сессии и сохранения после трёх refresh.
Проверены запрет использования разрешения другим входом того же аккаунта,
конфликт старой версии, выход, деактивация, смена роли и пароля.
С учётом отдельно добавленной миграционной проверки покрыты **252 различных
backend-сценария**. Тестовые БД удалены; рабочий сервер обновлён, TLS проверен,
backend-образ Docker пересобран.
Разбор устройства приложения для защиты: [LAB2-DEFENSE.md](LAB2-DEFENSE.md).

## Полная повторная проверка — 30.10.2026

Обязательные пункты ТЗ подтверждены перечисленными ниже проверками. При этом
был обнаружен дополнительный функциональный дефект: обновление JWT во время
редактирования делает выданное разрешение на сохранение ЭМК непригодным.
Это исторический результат этапа перепроверки; исправление описано выше.

### Найденный дефект: сохранение ЭМК после refresh — P2

Воспроизведено через реальный HTTPS в отдельной Docker-копии:

1. Активный врач входит в систему.
2. POST `/api/patients/{id}/medical-record/unlock` возвращает разрешение и версию.
3. POST `/api/user-auth/refresh` успешно меняет access и refresh.
4. PUT той же ЭМК с исходным разрешением, той же версией и новыми действующими
   cookie возвращает **403**, хотя роль врача и версия карты не изменились.

Причина: `backend/app/medical_records/router.py:127` сравнивает jti разрешения
с jti текущей пары токенов. Refresh создаёт новую запись с новым jti в
`backend/app/user_auth/service.py:37`, поэтому сравнение перестаёт выполняться.
Это может произойти и при обычном автоматическом обновлении истёкшего access,
пока врач редактирует ещё действующее разрешение ЭМК.

В UI 403 не приводит к получению нового разрешения. Отмена редактирования
сбрасывает форму (`frontend/src/pages/MedicalRecord/MedicalRecord.tsx:131`).
Следовательно, продолжить сохранение без повторной разблокировки нельзя,
а при отмене можно потерять несохранённые изменения.

Варианты исправления: связать разрешение со стабильным идентификатором сессии,
сохраняемым при ротации пары, либо безопасно обновлять разрешение при сохранении,
повторно проверяя роль, авторство сессии и текущую версию карты. Нельзя просто
удалить проверку принадлежности разрешения аккаунту/сессии.
На этапе перепроверки код приложения не исправлялся. По следующему запросу
дефект устранён; текущее поведение и новые проверки описаны в начале документа.

## Исправления и проверки

1. Все JWT (включая разрешение редактирования ЭМК) подписываются EdDSA / Ed25519.
   Закрытый ключ применяется для подписи, открытый — для проверки; HS256 не принимается.
   Ключевая пара сохраняется при перезапуске. Проверены подмена подписи, алгоритма,
   аудитории, истёкший срок и использование refresh вместо access.
2. Администратор получает access/refresh JWT после пароля и TOTP; обновление меняет
   оба токена. Повтор старого refresh и использование отозванного access отклоняются.
   Автообновление добавлено в клиент, включая переподключение SSE аудита.
3. Имя и фамилия медработника допускают 1–24 символа в форме, API и PostgreSQL.
   Должность по-прежнему требует 3–24. Проверены создание/изменение с 1–2 символами,
   миграция старых CHECK-ограничений и повторный запуск миграции.

Миграция сохраняет пароли, TOTP и медицинские данные. Старые HS256-токены
и непрозрачные административные сессии отзываются; требуется повторный вход.
