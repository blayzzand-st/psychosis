# PsychosIS: frontend

Минимальное приложение на React + TypeScript + Vite + MUI + React Router.

## Запуск

В папке frontend:

```powershell
npm.cmd ci
npm.cmd run dev
```

Страница: http://127.0.0.1:5173.
npm.cmd — Windows-команда npm, которая не требует запуска PowerShell-скрипта npm.ps1.
После первой установки повторять npm.cmd ci нужно только при изменении зависимостей
или на новом компьютере. Точные версии зафиксированы в package-lock.json.

Для проверки соединения бэкенд должен работать на http://127.0.0.1:8000.
В отдельном терминале из папки backend:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Оба сервера останавливаются через Ctrl+C в своих терминалах.

## Стартовая страница

Home предлагает два режима работы: «Администратор» и «Врач».
Каждая страница открывается по своему адресу:

| Адрес | Страница |
| --- | --- |
| / | Home — выбор роли |
| /administrator | Admin — администратор |
| /administrator/medical-workers/new | Создание медработника |
| /administrator/medical-workers/:workerId | Карточка и редактирование медработника |
| /administrator?section=directories | Раскрытое подменю справочников; рабочая область пуста |
| /administrator?section=directories&directory=diagnoses | Реестр диагнозов |
| /administrator/diagnoses/new | Создание диагноза |
| /administrator/diagnoses/:diagnosisId | Карточка и редактирование диагноза |
| /personal | Personal — список пациентов врача |
| /personal/patients/new | Создание пациента |
| /personal/patients/:patientId | Карточка и редактирование пациента |
| /personal/patients/:patientId/medical-record | Создание и просмотр ЭМК пациента |

Карточки ролей — ссылки React Router. Их можно открыть в новой вкладке.
Прямое открытие адресов и обновление страницы поддерживаются dev-сервером Vite.
Выбор администратора открывает страницу Admin с левым меню:
«Список медработников» и «Справочники». Выбранный раздел подсвечивается.
В разделе медработников список загружается из GET /api/medical-workers:
для каждого сотрудника отображаются имя, фамилия и должность.
Предусмотрены состояния загрузки, пустого списка и ошибки с повтором запроса.
По умолчанию отображаются активные сотрудники. Переключатель «Показать неактивные записи»
загружает список с include_deleted=true и фильтрует его на фронтенде:
отображаются только записи с is_deleted=true, с пометкой «Не активен».
Состояние переключателя хранится в URL и сохраняется при возврате из карточки.
При возвращении в раздел список загружается заново.
Нажатие «Справочники» раскрывает вложенное меню слева и очищает рабочую область.
«Реестр диагнозов» открывает реестр из этого подменю.
Повторное нажатие «Справочники» сворачивает подменю и очищает рабочую область;
состояние свёрнутого подменю хранится в URL как collapsed=true.
Выбранный подраздел хранится в URL, поэтому возврат из карточки диагноза открывает реестр.
Экран врача содержит левое меню с единственным разделом «Список пациентов».
Справа отображаются список и кнопка добавления; на узких экранах меню располагается над списком.
На обоих экранах есть кнопка «Назад» сверху слева.
Логотип в хедере — ссылка на стартовую страницу.
Кнопка «Назад» возвращает по истории навигации. При первом прямом открытии страницы
возвращает на Home.
В карточке медработника при прямом открытии кнопка возвращает к списку.

## Сценарий 1: управление медработниками

1. Откройте «Администратор» → «Список медработников».
2. Нажмите на сотрудника: откроется его карточка по отдельному URL.
3. Измените имя, фамилию или должность и нажмите «Сохранить изменения».
4. Для создания используйте «Добавить медработника» в списке.
5. Для удаления нажмите «Удалить» справа от имени в хедере карточки и подтвердите действие.

Все три поля обязательны. Имя и фамилия содержат от 3 до 24 символов;
пробелы по краям убираются перед сохранением. Должность выбирается из списка:
«Заведующий диагностикой», «Врач-диагност», «Заведующий терапией», «Врач-терапевт».
Список пока задан в коде на основе должностей текущих сотрудников.
Тип MedicalWorkerPosition выводится из этого списка и используется в типах API и форме.
Бэкенд проверяет обязательность и длину всех трёх полей.
«Отмена» возвращает к списку без сохранения введённых изменений.
Ошибки запроса отображаются в интерфейсе; введённые данные сохраняются в форме.

Форма отправляет POST при создании и PUT при редактировании.
После создания открывается карточка с ID, полученным от сервера.
Удаление вызывает DELETE, а бэкенд устанавливает is_deleted = true.
Строка остаётся в SQLite, но не попадает в обычный список.
Карточка удалённого сотрудника открывается из списка с включённым переключателем
«Показать неактивные записи» и доступна только для просмотра. Для её загрузки GET-запрос
использует include_deleted=true; PUT и DELETE для удалённых записей возвращают 404.
Кнопка «Восстановить» справа от имени отправляет POST /api/medical-workers/{id}/restore.
После успешного ответа карточка становится редактируемой, а сотрудник снова
попадает в активный список. При ошибке доступна повторная попытка.
Повторное открытие страницы загружает сохранённые данные из API.

## Сценарий 2: реестр диагнозов

В «Администратор» → «Справочники» → «Реестр диагнозов» отображаются наименование и код каждого диагноза.
Строка открывает карточку с общей оболочкой DetailsCard.
«Добавить диагноз» открывает пустую форму; код содержит ровно 6 символов,
наименование — от 3 до 128. Оба значения обязательны и уникальны.
Код перед отправкой переводится в верхний регистр, пробелы по краям убираются.
Конфликт уникальности отображается в форме без потери введённых данных.

«Удалить» находится справа от наименования. Подтверждение сообщает о полном
удалении без восстановления. После DELETE запись физически исчезает из БД,
а интерфейс возвращается к реестру. Фильтра неактивных записей здесь нет.
Начальные пять примеров МКБ-11 2026-01 загружаются командой из backend/README.md.
Список поддерживает состояния загрузки, пустого реестра и ошибки с повтором запроса.

## Сценарий 3: пациенты

Home → «Врач» открывает список пациентов. Строка содержит ФИО, дату рождения
и административный пол; нажатие открывает отдельную карточку.
«Добавить пациента» открывает форму создания. Карточка использует общий DetailsCard.

Имя и фамилия обязательны, от 1 до 64 символов; отчество необязательно.
Дата рождения обязательна и не может быть в будущем.
Административный пол выбирается из списка: «Мужской», «Женский», «Не установлен»;
в API это М, Ж, НУ. Комментарий необязателен, ограничен 32 символами.
Форма и API проверяют значения; ошибки показываются без потери введённых данных.
«Отмена» возвращает к списку без сохранения изменений.

«Удалить» находится справа от ФИО. Удаление физическое, после подтверждения.
Если API сообщает has_medical_record=true, кнопка недоступна, а карточка
объясняет причину. API независимо запрещает DELETE пациента с ЭМК и возвращает 409.
Из карточки пациента можно создать или открыть его ЭМК.
Список поддерживает загрузку, пустое состояние и повтор запроса после ошибки.

## Сценарий 4: ЭМК

1. Откройте пациента и нажмите «Создать ЭМК». Выберите действующего медработника
   и подтвердите создание. Без выбора кнопка недоступна. У пациента может быть только одна карта.
2. Созданная карта и любое повторное открытие доступны в режиме просмотра.
   Диагнозы и назначения заблокированы.
3. Выберите медработника и нажмите «Разблокировать». Его ID станет автором сохранения.
   Выбор автора недоступен до сохранения или отмены текущего редактирования.
4. Выберите диагнозы из реестра, добавьте или измените строки назначений (3–128 символов).
5. «Сохранить» отправляет содержимое, ID медработника и прочитанную версию карты.
   После успешного ответа поля снова заблокированы, выбранный медработник сброшен.
   «Отмена» возвращает сохранённое содержимое и блокировку без запроса сохранения.

Показываются время последнего сохранения (Москва) и автор.
После перезагрузки страницы содержимое загружается из API и остаётся заблокированным.
При конфликте версий изменения не затираются. Кнопка «Обновить карту» явно отбрасывает
локальный черновик, загружает актуальную версию и возвращает режим просмотра.
Отсутствие активных медработников запрещает создание и разблокировку, но не просмотр карты.

Блокировка — локальное состояние страницы, не серверная авторизация.
API отдельно требует существующего действующего медработника для любых изменений ЭМК.
После создания карты кнопка удаления пациента недоступна, сервер независимо запрещает DELETE.

## Сценарий 5: диагнозы, назначения и история ЭМК

Содержимое карты разделено на вкладки «Диагнозы», «Назначения» и «История изменений».
Переключение не сбрасывает черновик. «Сохранить» на любой из первых двух вкладок
сохраняет оба списка; ошибка в назначении автоматически открывает его вкладку.
История загружается при выборе вкладки, без дополнительной кнопки раскрытия.

1. Разблокируйте ЭМК, выбрав действующего медработника.
2. На вкладке «Диагнозы» отображается единый список без подзаголовков: актуальные
   диагнозы с зелёным статусом и датой постановки, ниже — красный статус «Не актуален»
   и даты постановки / удаления у прежних диагнозов.
   После разблокировки выберите запись в поле «Добавить диагноз» или нажмите
   «Удалить» у актуального диагноза. Это меняет карту, не справочник.
   До сохранения отображаются статусы «Будет добавлен» / «Будет удалён»;
   «Вернуть» отменяет несохранённое удаление.
3. «Добавить назначение» добавляет строку. Текст можно изменить, а «Отменить»
   рядом со строкой убирает назначение из текущего списка. До сохранения отображается
   статус изменения, а «Вернуть» отменяет несохранённую отмену назначения.
4. Нажмите «Сохранить». Сервер запишет снимок и журнал действий, затем карта
   заблокируется. «Отмена» под формой отбрасывает весь несохранённый черновик.
5. Вкладка «История изменений» открывает сохранения от новых к старым с временем (Москва),
   медработником и списком конкретных действий. Изменение текста назначения
   отображается как отмена прежнего и добавление нового.
6. «Посмотреть версию» показывает полный список диагнозов и назначений после
   выбранного сохранения. Поле «Состояние на момент (Москва)» и кнопка
   «Показать состояние» позволяют выбрать произвольную дату и время.

Историческое состояние выводится отдельным блоком только для просмотра:
текущая карта и черновик не перезаписываются. Время поля интерпретируется как
московское независимо от часового пояса браузера. До создания карты показывается
понятное сообщение об отсутствии ЭМК на этот момент.
Журнал обновляется после сохранения; ошибки загрузки допускают повторную попытку.
Тексты старых назначений и данные диагнозов остаются в истории после отмены / удаления.
История также сохраняет имя и должность автора на момент сохранения.

Обзор диагнозов строится по снимкам истории до версии, открытой в форме.
Дата постановки сохраняется при обычном сохранении ЭМК, а повторная постановка
после удаления создаёт отдельный эпизод. Старые наименования и коды сохраняются.
Актуальные диагнозы показываются первыми, новые — выше; удалённые упорядочены
по последнему удалению. Даты отображаются по Москве. Авторы отдельных действий
доступны во вкладке истории, в обзорных строках их нет.
При ошибке загрузки хронологии текущие диагнозы остаются видны, а даты и удалённые
записи можно загрузить повторно. Неизвестные даты не подменяются временем открытия страницы.

Вкладка «Назначения» устроена аналогично: единый список без подзаголовков,
зелёное «Актуально» и дата назначения, затем красное «Не актуально» и даты
назначения / отмены. При изменении текста прежнее назначение остаётся среди
неактуальных, новое получает дату последнего сохранения. Повторное добавление
того же текста также создаёт новый эпизод. Автор конкретного действия доступен в истории.
В режиме редактирования текст вводится в однострочное поле (3–128 символов).
Черновик, включая отменённые до сохранения строки, сохраняется между вкладками.

Для новых версий соответствие одинаковых строк определяется по сохранённым
prescription_sources. Для прежних версий используются снимки и действия журнала.
Если в старой истории невозможно отличить одинаковые строки с разными датами,
обзор показывает «дата неизвестна», не приписывая строке произвольную дату.

## Как работает проверка соединения на странице Test

1. Обработчик в pages/Test/Test.tsx меняет состояние на checking, и React обновляет страницу.
2. fetch отправляет GET /api/health на адрес фронтенда.
3. Dev-сервер Vite перенаправляет запрос на бэкенд через proxy в vite.config.ts.
4. Бэкенд возвращает JSON {"status":"ok"}.
5. Обработчик меняет состояние на online или error, и React показывает результат.

Ожидание ограничено пятью секундами. Во время проверки кнопка отключена.
Этот запрос подтверждает доступность API; работу БД он не проверяет.
Proxy используется только при разработке. Для размещения приложения потребуется
отдельно настроить маршрут /api к бэкенду.

## Основные файлы

- index.html — HTML-страница с контейнером root.
- src/main.tsx — подключает React к контейнеру и отображает App.
- src/App.tsx — маршруты страниц и подключение общего PageLayout.
- src/pages/Home/Home.tsx — стартовая страница с выбором роли.
- src/pages/Home/Home.styles.ts — styled-компоненты стартовой страницы.
- src/pages/Admin/Admin.tsx — страница администратора и переключение разделов.
- src/pages/Admin/Admin.styles.ts — оформление страницы администратора и левого меню.
- src/pages/Admin/MedicalWorkerList/ — загрузка и отображение списка медработников.
- src/pages/MedicalWorker/ — загрузка карточки, создание, сохранение и подтверждение удаления.
- src/pages/MedicalWorker/MedicalWorkerForm/ — поля формы и проверка их длины.
- src/pages/Admin/DiagnosisList/ — список диагнозов из API.
- src/pages/Diagnosis/ — карточка диагноза, создание, редактирование и физическое удаление.
- src/api/diagnoses.ts — типы диагнозов и CRUD-запросы.
- src/api/medicalWorkers.ts — типы, CRUD-запросы к API и обработка ошибок сервера.
- src/types/medicalWorkerPosition.ts — список должностей и отдельный TypeScript-тип.
- src/pages/Personal/Personal.tsx — отдельная страница врача.
- src/pages/Personal/Personal.styles.ts — оформление страницы врача.
- src/pages/Personal/PatientList/ — загрузка списка пациентов и переходы в карточки.
- src/pages/Patient/ — создание, редактирование и удаление пациента.
- src/pages/MedicalRecord/ — создание ЭМК, выбор автора, блокировка и сохранение.
- src/pages/MedicalRecord/MedicalRecordForm/ — списки диагнозов и назначений, проверка строк.
- src/pages/MedicalRecord/MedicalRecordHistory/ — журнал действий и просмотр состояния по версии или времени.
- src/pages/MedicalRecord/MedicalRecordDiagnoses/ — обзор актуальных и удалённых эпизодов, их даты и редактирование списка.
- src/pages/MedicalRecord/MedicalRecordPrescriptions/ — обзор актуальных и отменённых назначений, их даты и редактирование.
- src/api/medicalRecords.ts — запросы ЭМК, содержимое, версия и ошибки.
- src/api/patients.ts — типы, запросы CRUD и ошибки полей пациента.
- src/types/patient.ts — отдельный тип административного пола и варианты выбора.
- src/pages/Test/Test.tsx — тестовая страница, состояние и запрос к API.
- src/pages/Test/Test.styles.ts — styled-компоненты страницы на MUI.
- src/shared/ui/BackButton/ — переиспользуемая кнопка возврата с SVG-стрелкой.
- src/shared/ui/DetailsCard/ — общая карточка с заголовком, действием справа и содержимым; используется для медработников, диагнозов и пациентов.
- src/shared/config/routes.ts — общий адрес реестра для навигации и возврата из карточки диагноза.
- src/shared/ui/PageLayout/ — общий хедер и контейнер страниц.
- src/theme.ts — общая палитра, шрифт и глобальные настройки MUI.
- vite.config.ts — настройки сервера разработки и proxy.
- package.json — зависимости и команды проекта.

ThemeProvider передаёт тему компонентам, CssBaseline задаёт базовые стили страницы.

Проверка TypeScript и сборка: npm.cmd run build.
Проверка хронологии диагнозов и назначений: npm.cmd test (встроенный test runner Node.js, без дополнительных пакетов).
