# PsychosIS: backend

FastAPI + SQLAlchemy + PostgreSQL. Подключение задаётся переменной DATABASE_URL
в backend/.env; файл читается независимо от рабочей папки при запуске.
Пароли, резервные копии и локальные файлы PostgreSQL исключены из Git.
Приложение и тесты работают только с PostgreSQL (драйвер psycopg).

## Локальная база PostgreSQL (Windows)

PostgreSQL установлен в `%LOCALAPPDATA%\PsychosIS\PostgreSQL`:
путь латиницей необходим из-за ошибки initdb с кириллицей в пути проекта.
Данные находятся в подпапке `pgdata`. Сервер слушает только `127.0.0.1:5432`.
База и пользователь приложения — `psychosis`; пароль сгенерирован в backend/.env.
Файл `.local/postgres-runtime.txt` указывает расположение локального сервера.
Автозапуск Windows не настроен. После перезагрузки из корня проекта:

```powershell
.\start-postgres.ps1
```

Остановка: `.\stop-postgres.ps1`. Затем backend запускается как показано ниже.
На другом компьютере установите PostgreSQL, создайте базу и настройте `.env`
по `.env.example`. Локальная установка и данные через Git не передаются.

## База данных

Поддерживается только URL вида `postgresql+psycopg://...`. Другие драйверы
отклоняются при запуске. Таблицы создаются при старте приложения.
Резервные копии и архив прежней базы находятся в `backend/backups`
и не используются приложением.


## Установка и запуск

Из папки backend, с установленным Python:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Если окружение уже настроено, нужна только последняя команда.
Документация и ручная проверка API: http://127.0.0.1:8000/docs.
При старте создаются отсутствующие таблицы. Саму базу PostgreSQL нужно создать заранее.
Существующие данные сохраняются.
create_all не обновляет структуру уже существующих таблиц: при изменении схемы
понадобятся миграции.

## Медработник

| Поле | Правила |
| --- | --- |
| id | Положительный идентификатор, назначается сервером |
| first_name | Имя, от 3 до 24 символов |
| last_name | Фамилия, от 3 до 24 символов |
| position | Должность, от 3 до 24 символов |
| is_deleted | Признак логического удаления, управляется сервером |

Пробелы по краям текстовых полей убираются перед проверкой длины.
Все три поля обязательны при создании и редактировании. Неизвестные поля,
переданные клиентом id и is_deleted отклоняются.
Ограничения длины проверяются как API, так и CHECK-ограничениями PostgreSQL.

id нужен для адресации карточки и будущих ссылок из ЭМК.
is_deleted позволяет скрыть медработника, сохранив запись для истории ЭМК.

## API

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /api/health | Проверка доступности приложения, 200 |
| POST | /api/medical-workers | Создание, 201 |
| GET | /api/medical-workers | Список активных медработников, 200 |
| GET | /api/medical-workers/{id} | Карточка активного медработника, 200 |
| PUT | /api/medical-workers/{id} | Полная замена трёх редактируемых полей, 200 |
| DELETE | /api/medical-workers/{id} | Установка is_deleted=true, 204 без тела |
| POST | /api/medical-workers/{id}/restore | Восстановление: is_deleted=false, карточка, 200 |

Для создания и редактирования:

```json
{
  "first_name": "Иван",
  "last_name": "Петров",
  "position": "Терапевт"
}
```

GET /api/medical-workers?include_deleted=true включает удалённые записи в список.
GET /api/medical-workers/{id}?include_deleted=true позволяет просмотреть удалённую карточку.
Удалённая запись остаётся в БД, но обычное чтение по ID, редактирование
и повторное удаление возвращают 404, как и для отсутствующего ID.
Неверные поля или неположительный ID возвращают 422.
Восстановление сохраняет ID, имя, фамилию и должность. Сотрудник снова появляется
в активном списке и доступен для редактирования. Повторное восстановление уже
активного сотрудника возвращает ту же карточку; отсутствующий ID возвращает 404.
Авторизация по условиям ЛР1 не требуется.

## Как устроен запрос

1. FastAPI и Pydantic проверяют JSON по схеме из schemas.py.
2. get_session открывает отдельную сессию БД для запроса.
3. Обработчик из router.py читает или меняет ORM-модель MedicalWorker.
4. commit сохраняет изменения транзакции; refresh перечитывает запись из БД.
5. MedicalWorkerRead определяет поля JSON-ответа.
6. После завершения запроса сессия закрывается. Незавершённая транзакция откатывается.

database.py содержит подключение и базовый класс моделей.
medical_workers/models.py описывает таблицу, schemas.py — контракт данных,
router.py — CRUD и правила логического удаления.
main.py собирает приложение и создаёт таблицы при старте.

## Реестр диагнозов

Диагноз хранится в таблице diagnoses: id, code (ровно 6 символов, уникален),
name (от 3 до 128 символов, уникально). Лимит наименования увеличен с 24 до 128
по согласованию, чтобы хранить полные названия, включая системную красную волчанку.
Пробелы по краям убираются, код приводится к верхнему регистру до проверки длины.
Ограничения длины и уникальности действуют также в PostgreSQL.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /api/diagnoses | Реестр, 200 |
| POST | /api/diagnoses | Создание, 201 |
| GET | /api/diagnoses/{id} | Карточка, 200 |
| PUT | /api/diagnoses/{id} | Изменение кода и наименования, 200 |
| DELETE | /api/diagnoses/{id} | Физическое удаление строки из БД, 204 |

Невалидные поля дают 422, повтор кода или наименования — 409,
отсутствующий ID — 404. При конфликте изменения откатываются.
У диагноза нет is_deleted и операции восстановления.
После удаления его код и наименование можно использовать снова.

Начальные примеры загружаются явно из папки backend:

```powershell
.\.venv\Scripts\python.exe -m app.diagnoses.seed
```

Повторный запуск пропускает существующие коды и не меняет отредактированные записи.
Команда не запускается при старте сервера: удалённые диагнозы сами не возвращаются.
Повторная явная загрузка примеров добавит отсутствующие коды.

Источник примеров — [официальный файл МКБ-11 MMS ВОЗ, выпуск 2026-01](https://icdcdn.who.int/static/releasefiles/2026-01/SimpleTabulation-ICD-11-MMS-ru.zip).
Выбраны пять шестисимвольных кодов; это учебная выборка, не полный классификатор.

| Код | Наименование | Источник ВОЗ |
| --- | --- | --- |
| 4A40.0 | Системная красная волчанка | [МКБ-11](https://icd.who.int/browse/2026-01/mms/ru#749596428) |
| CA23.0 | Аллергическая астма | [МКБ-11](https://icd.who.int/browse/2026-01/mms/ru#1870104478) |
| CA40.0 | Бактериальная пневмония | [МКБ-11](https://icd.who.int/browse/2026-01/mms/ru#1323682030) |
| 8A80.0 | Мигрень без ауры | [МКБ-11](https://icd.who.int/browse/2026-01/mms/ru#2048783472) |
| DB10.0 | Острый аппендицит | [МКБ-11](https://icd.who.int/browse/2026-01/mms/ru#40398753) |

API проверяет длину и уникальность введённых значений; внешнего запроса к МКБ
при создании или редактировании нет. Код справочника можно менять вручную.

## Пациенты

| Поле | Правила |
| --- | --- |
| first_name, last_name | Обязательные, от 1 до 64 символов после удаления пробелов по краям |
| patronymic | Необязательное, до 64 символов; пустое значение хранится как null |
| date_of_birth | Обязательная календарная дата ГГГГ-ММ-ДД, не позднее текущей даты сервера |
| administrative_sex | Обязательное значение М, Ж или НУ (не установлен) |
| comment | Необязательное, до 32 символов; по умолчанию пустая строка |

Лимит имён выбран отдельно от медработников: разрешены короткие имена вроде «Ян» и фамилии вроде «Ли».
Служебные id и has_medical_record доступны только для чтения.
Одинаковые ФИО и даты рождения у разных пациентов допустимы; записи различаются по id.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /api/patients | Список, 200 |
| POST | /api/patients | Создание, 201 |
| GET | /api/patients/{id} | Карточка, 200 |
| PUT | /api/patients/{id} | Полная замена редактируемых полей, 200 |
| DELETE | /api/patients/{id} | Физическое удаление пациента без ЭМК, 204 |

Ошибки полей дают 422, отсутствующий ID — 404, удаление пациента с ЭМК — 409.
При PUT необязательные поля, которые не переданы, сбрасываются в значения по умолчанию.

Связь с ЭМК хранится в medical_records(id, patient_id): patient_id уникален,
ссылается на patients.id с ON DELETE RESTRICT.
has_medical_record вычисляется по связи, клиент не может изменить его произвольным JSON.
DELETE проверяет наличие ЭМК на сервере. PostgreSQL также блокирует
удаление связанного пациента внешним ключом, включая прямой SQL.
У пациентов нет логического удаления и восстановления.

## ЭМК: сценарий 4

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | /api/patients/{id}/medical-record | Прочитать текущее содержимое ЭМК |
| POST | /api/patients/{id}/medical-record | Создать пустую ЭМК, передав worker_id |
| PUT | /api/patients/{id}/medical-record | Сохранить списки диагнозов и назначений с worker_id и version |

У пациента не более одной ЭМК. Повторное создание даёт 409, отсутствующий пациент
или карта — 404. После создания карты удаление пациента запрещено.
worker_id обязателен при создании и сохранении, должен указывать на существующего
не удалённого медработника. Без него или с неподходящим медработником запрос даёт 422.
Нет требования авторизации; worker_id указывается пользователем явно.

Пример тела PUT:

```json
{
  "worker_id": 1,
  "version": 1,
  "diagnosis_ids": [1],
  "prescriptions": ["Контроль состояния"]
}
```

Назначение — строка от 3 до 128 символов, пробелы по краям убираются.
Повтор одного диагноза в списке и отсутствующий новый диагноз дают 422.
Списки могут быть пустыми. PUT сохраняет содержимое целиком одной транзакцией.

Блокировка редактирования существует только в интерфейсе, как требует ТЗ.
В БД нет is_locked и серверного владельца блокировки. API принимает изменения
с действующим worker_id независимо от состояния интерфейса.
Проверка версии — отдельная защита от потери изменений при работе из двух вкладок:
клиент передаёт version, которую прочитал, а сервер при несовпадении возвращает 409.
Уникальность пары (medical_record_id, version) защищает и от одновременных сохранений.

Таблица medical_records сохраняет прежние id и patient_id. Новая таблица
medical_record_revisions хранит полные снимки диагнозов и назначений, автора,
его ФИО и должность на момент изменения, время в UTC, действие created/saved и версию.
Создание даёт версию 1, каждое сохранение добавляет новую; предыдущие снимки не меняются.
Текущее содержимое — снимок с максимальной версией. Карта старой модели без снимков
читается пустой с версией 0; первое сохранение создаёт её первую версию.

Код и наименование диагноза копируются в снимок ЭМК. Последующее изменение или
удаление строки из реестра не переписывает сохранённую карту и предыдущие снимки.
При сохранении уже имеющиеся диагнозы сохраняют свои снимки, новые проверяются по реестру.
Новая таблица создаётся при старте; перестройка прежних таблиц не требуется.

## ЭМК: сценарий 5 — операции и история

Изменения клинических списков отправляются тем же PUT ЭМК. До нажатия «Сохранить»
они остаются черновиком интерфейса. При сохранении сервер сравнивает новое содержимое
с предыдущей версией и в одной транзакции записывает снимок и конкретные действия:

- diagnosis_added / diagnosis_removed — добавлен / удалён диагноз;
- prescription_added / prescription_cancelled — добавлено / отменено назначение;
- record_created — создана карта;
- record_saved — сохранение без изменения списков.

Редактирование назначения записывается как prescription_cancelled со старым текстом
и prescription_added с новым. Одинаковые строки назначений допустимы: сравнение
учитывает количество повторений, поэтому отмена одной из двух одинаковых строк
не отменяет вторую. Перестановка строк сохраняется в снимке и не считается отменой.

Форма также передаёт prescription_sources: для каждой новой строки это null,
для существующей — индекс в списке предыдущей версии. Это служебные ссылки,
действительные только вместе с проверяемой version. Сервер проверяет длину списка,
диапазон и уникальность ссылок. Они позволяют различить, например, изменение
первого назначения в текст второго с одновременной отменой второго назначения.
Без ссылок одинаковый конечный список не показывает, какую строку редактировали.
Для прежних клиентов без этого необязательного поля и для старых снимков журнал
строится по разнице содержимого с учётом количества одинаковых строк.

Для новых сохранений ссылки также записываются в medical_record_prescription_links:
revision_id — уникальный внешний ключ версии, sources — JSON-массив индексов / null.
Это позволяет обзору назначений сохранять дату конкретной строки, даже когда тексты
двух назначений совпадают или строки переставлены. Редактирование текста по-прежнему
закрывает прежнее назначение и создаёт новое. Ссылки записываются той же транзакцией,
что снимок и действия, и доступны в GET истории как prescription_sources.
Таблица создаётся при старте; прежние снимки и действия не переписываются.

Таблицы разделяют ответственность:

| Таблица | Что хранит |
| --- | --- |
| medical_records | Единственную карту пациента |
| medical_record_revisions | Полное состояние после сохранения, версию, время UTC и снимок автора |
| medical_record_changes | Действия конкретной версии, их порядок и данные диагноза / текст назначения |
| medical_record_prescription_links | Связи строк назначений с предыдущей версией для сохранения их дат |

Каждое действие связано с версией через revision_id; дата, время и автор берутся
из этой версии. ordinal задаёт порядок действий внутри одного сохранения.
Предыдущие снимки и действия через API не редактируются и не удаляются.
Удаление диагноза из ЭМК меняет её текущий список, не справочник диагнозов.
Отмена назначения убирает его из текущего списка, но оставляет прежний текст в истории.
Изменение или удаление данных справочника и логическое удаление медработника
не меняют сохранённые названия, коды, тексты и снимки автора.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /api/patients/{id}/medical-record/history | Все версии по возрастанию, снимки и действия |
| GET | /api/patients/{id}/medical-record?at=2026-10-16T10:00:00Z | Состояние на выбранный момент |

Параметр at — ISO 8601 с обязательным часовым поясом (Z или смещение).
Он переводится в UTC. Сервер выбирает последнюю сохранённую версию с временем
не позже at. На границе сохранения возвращается новая версия, между сохранениями —
предыдущая. До первого сохранения возвращается 404; некорректное время или время
без часового пояса даёт 422. Без at GET возвращает актуальную карту.
Чтение прежнего состояния не перезаписывает текущую ЭМК.

При первом старте после добавления сценария 5 создаётся medical_record_changes.
Для существующих версий журнал достраивается сравнением сохранённых снимков;
исходные версии, авторы и времена сохраняются. Повторный старт не дублирует журнал.
История начинается с первого сохранённого снимка: для старого пустого заголовка
ЭМК без версий время создания неизвестно, и выдуманная история не добавляется.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты работают только с PostgreSQL. Перед запуском создайте отдельную базу
`psychosis_test` с владельцем — пользователем приложения (один раз):

```sql
CREATE DATABASE psychosis_test OWNER psychosis;
```

Задайте `TEST_DATABASE_URL` в `backend/.env` по образцу `.env.example`.
Без этой настройки тесты завершатся ошибкой с объяснением.
Имя тестовой базы должно отличаться от рабочей; совпадение отклоняется.
Каждый тест создаёт свою схему
и удаляет её после завершения; рабочую базу для тестов не используйте.
Проверяют CRUD, границы длины, обязательные и служебные поля,
логическое удаление, чтение удалённой карточки, запрет её изменения
и сохранность данных после перезапуска приложения.
Рабочая база при этих проверках не используется.
Тесты диагнозов также проверяют физическое удаление, конфликты уникальности,
явную повторяемую загрузку примеров и отсутствие автоматического восстановления после перезапуска.
Тесты ЭМК проверяют обязательного действующего автора, единственную карту пациента,
сохранение списков, снимки прежнего содержимого, конфликт версий и сохранность после перезапуска.
Тесты истории проверяют все операции, редактирование как отмену и добавление,
повторяющиеся назначения, выбор состояния по времени (включая точные границы
и часовые пояса), сохранность после изменения справочников и автора,
отсутствие записей при отклонённом запросе и повторяемое достроение старого журнала.
